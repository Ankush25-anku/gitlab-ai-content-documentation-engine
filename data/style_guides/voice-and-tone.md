# Voice and tone guide

## Principles

Write for a busy, technical reader who scans first. Be direct, specific and correct. Prefer short sentences in active voice. Address the reader as "you".

## Word choice

Use the GitLab terms in the glossary exactly. Say "merge request", never "pull request". Say "select" for UI actions, not "click". Avoid words that judge difficulty, such as "simply", "just" and "easy".

## Claims

State only what the feature does. Do not promise performance, security or compatibility unless a source states it. Name the tier and offering when a feature is not available everywhere.

## Formatting

Use sentence case for headings. Use numbered lists for steps and tables for parameters. Put code, file names, keywords and UI-independent values in code format.

## Channel differences

Documentation is neutral and task-focused. Release notes lead with the user benefit. Blogs are conversational and tell a story. API references are terse and exact. Onboarding guides are encouraging and assume no prior knowledge.
